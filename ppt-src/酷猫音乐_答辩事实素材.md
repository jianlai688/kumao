# 酷猫音乐平台 · 5 人分端答辩事实素材

> 本文件是答辩 PPT 的唯一事实来源（事实取自项目仓库 README.md、docs/架构说明.md、docs/部署运行说明.md、酷猫音乐平台_微服务模块需求分析.txt 与代码统计）。

## 一、作品与团队

- 作品名：酷猫音乐（KUMAO MUSIC），一个「音乐 + 直播 + 内容创作 + 广告变现」的一体化在线音乐平台。
- 交付形态：PC Web 用户端 + 运营管理后台（同一 Vue3 工程双端）+ uniapp APP（H5/小程序/Android APK）+ Electron 桌面端 + 1 个网关 + 11 个 Spring Cloud 微服务。
- 团队规模：5 人，**按角色端分工**——一人负责一个端，端内前端页面、后端服务、接口联调、答辩讲解全流程闭环，端与端之间通过统一网关和 Feign 契约协作。
- 分工（占位姓名，可替换）：
  | 成员 | 负责端 | 一句话职责 |
  |---|---|---|
  | 成员A（组长） | 用户端 | 听众侧全部体验：发现、播放、榜单、歌单、MV、搜索、会员、观看直播，PC/APP/桌面三形态；兼任架构与联调统筹 |
  | 成员B | 管理员端 | 运营后台 20 个管理页面 + AI 内容审核工作台 + 全平台审核/权限/数据看板 |
  | 成员C | 广告达人端 | 广告制作人入驻、素材制作、投流投放、投放数据与收益提现 |
  | 成员D | 主播端 | 主播入驻审核、开播推流、直播控制台、弹幕互动、礼物与主播收益 |
  | 成员E | 音乐人端 | 音乐人入驻、作品/专辑管理、粉丝与播放数据、收益与提现 |

## 二、选题背景与目标

- 背景：主流音乐产品「听歌」与「直播」是两套体系，创作者（音乐人）、主播、广告制作人三类角色缺少统一的入驻—创作—变现闭环；课程/竞赛项目常见的做法是单体 Demo，无法体现真实平台的协作复杂度。
- 目标：用微服务架构一次性支撑 **5 个角色端**，让「听众听得爽、创作者赚得到、运营管得住」三件事在同一条链路上跑通。
- 关键约束：5 人、一个学期、无商业云服务预算，因此中间件全部本地容器化（Docker Compose 一键起 MySQL/Redis/Nacos/RabbitMQ/MinIO/Elasticsearch/Sentinel/SRS），支付走支付宝沙箱，AI 审核走可配置模型 + 本地规则降级。

## 三、总体架构

```
PC Web(Vue3)  APP(uniapp/APK)  桌面(Electron)
        └────────── HTTPS / WSS ──────────┘
                 kumao-gateway :8080
      路由 · JWT 鉴权 · 设备识别 · 专属接口隔离
      Sentinel 限流熔断降级 · CORS · WebSocket 转发
   ┌──────┬──────┬──────┬──────┬──────┬──────┐
 user  music playlist comment live  search ... 11 个业务微服务
   └──────┴──────┴──────┴──────┴──────┴──────┘
        MySQL8 / Redis7 / MinIO / RabbitMQ / ES8 / SRS5
```

- 微服务清单（12 个进程）：gateway 8080；user 8101、music 8102、playlist 8103、comment 8104、file 8105、live 8106、search 8107、vip 8108、musician 8109、ad 8110、review 8111。
- 技术栈：Spring Boot 3.2.5 / Spring Cloud 2023.0.1 / Spring Cloud Alibaba 2023.0.1.0、Nacos 注册配置、MyBatis-Plus 3.5.6、MySQL 8、Redis 7、MinIO、RabbitMQ、Elasticsearch 8、Sentinel、SRS 5、WebSocket；前端 Vue 3 + Vite + Element Plus + Pinia + ECharts，APP 用 uniapp，桌面端 Electron 壳。
- 统一鉴权：user-service 签发 JWT，payload 含 userId/username/role/device；网关 AuthGlobalFilter 校验并向下游透传 X-User-Id / X-Username / X-Role / X-Device；业务服务用 UserContextInterceptor 还原登录态，UserContext.requireUserId() / requireAdmin() 二次校验；多端登录按 device 维度存 Redis `kumao:login:token:{userId}:{device}`，EXCLUSIVE 策略下新设备登录踢掉其它设备。
- 限流降级：Sentinel 网关规则全局 200 QPS/IP，写接口（评论/弹幕/文件）30 QPS；阻塞处理器返回统一 JSON `{"code":429,"message":"访问过于频繁，请稍后再试"}`；user-service 路由再用 Redis 令牌桶做二级限流。
- 检索：ES 索引 kumao_search（统一文档结构 type + bizId），业务变更通过 /internal/search/sync 增量同步；ES 不可用时 FallbackSearchService 退化为 MySQL LIKE，后台支持手动全量重建索引。
- 异步：RabbitMQ 两个队列，kumao.play.record（播放记录落库 + 播放量 +1）、kumao.live.danmaku（弹幕异步落库）。
- 直播链路：主播 OBS ——RTMP—— SRS ——HTTP-FLV（低延迟）/ HLS（兜底）—— 观众播放器；SRS on_dvr 回调 live-service 生成回放；弹幕走 WebSocket(/ws/live)，先过 review-service AI 审核，PASS 才广播并异步落库，REVIEW/REJECT 落库 status=2 交管理员复核；在线人数用 Redis Set `kumao:live:online:{roomId}` 按会话增减；推流鉴权 HMAC-SHA256(stream:anchorId, pushKey)；敏感词用 DFA 前缀树。
- 数据库：单库 kumao_music，按模块分表共 44 张表（user/music/playlist/comment/file/live/vip/musician/ad 九组）。收益模型（模拟）：音乐人每 1000 次播放折算 10 虚拟币，直播礼物按 70% 折算；提现走「申请 → 管理员审核 → 生成负向收益流水」。

## 四、五个端逐端材料

### 1. 用户端（成员A，组长）

- 覆盖页面（PC 用户端 20 个视图 + APP 28 个页面 + 桌面壳）：首页/发现、排行榜、歌手与歌手详情、歌单列表与详情、MV 专区、搜索、歌曲详情与播放器（PlayerBar）、直播间与直播广场、会员 VIP、我的（收藏/歌单/下载/资料/角色档案）、音乐人主页、三个入驻申请页。
- 后端归属：music-service（歌曲/歌手/榜单/MV/歌词）、playlist-service（歌单与收藏）、search-service（全文检索）、comment-service（评论/我喜欢/播放记录）、vip-service（会员套餐与支付）、file-service（头像与封面上传）。
- 核心亮点：
  - 三端一套 API：PC Web、uniapp APP、Electron 桌面共用同一网关与接口，仅 device 标识不同，桌面端可访问 DESKTOP 专属接口。
  - 播放与榜单：榜单缓存 Redis 快照，播放记录走 RabbitMQ 异步落库并累加播放量，不阻塞播放。
  - 搜索体验：关键词一次检索歌曲/歌手/歌单/直播间/音乐人五类实体，ES 挂了自动降级 MySQL 模糊匹配，用户无感。
  - 会员与支付：支付宝沙箱/微信支付下单 → 回调 → 开通会员，订单幂等；高清 MV 播放前向 vip-service 校验权益。
  - 首页运营位：今日主打轮播、顶部 Banner、广告位（开屏/首页/直播页/播放页）由后台配置下发，前端按位渲染。
- 可演示点：APP 首页发现流 → 搜索 → 播放页歌词与音质 → 收藏到歌单 → 开通会员看高清 MV → 进直播间看弹幕。
- 难点：多端一致性（同一组件库在三形态下的自适应）、播放器状态与路由解耦、搜索降级时的结果排序对齐。

### 2. 管理员端（成员B）

- 覆盖页面：运营后台 20 个管理页面——数据看板、AI 审核工作台、用户管理、主播审核、音乐人管理、广告管理、歌曲管理（含文件夹批量上传）、歌手管理、MV 管理、轮播管理、首页设置、歌单管理、评论管理、直播管理、礼物管理、会员管理、文件管理、搜索监控、AI 模型配置、广告主管理。
- 后端归属：review-service（AI 内容审核、自动审核调度、模型配置、审核日志）、user-service（角色与权限、主播/音乐人/广告商身份证正反面认证审核）、file-service（素材）、search-service（索引重建与监控），并对 11 个服务做统一审核动作。
- 核心亮点：
  - AI 审核工作台：评论/弹幕/MV 先由 review-service 判定 PASS / REVIEW / REJECT，风险内容进人工复核队列，支持一键通过/驳回/禁言，审核日志全程留痕；模型不可用时本地规则兜底，不阻断业务。
  - 批量内容运营：歌曲支持「文件夹批量上传」，自动解析歌手、专辑、封面，逐条确认后入库并同步 ES 索引。
  - 首页可视化配置：轮播开关、切换间隔、轮播条数、热歌榜自动/手动选题，保存后 PC 与 APP 首页即时生效。
  - 全平台数据看板：ECharts 展示播放、直播、广告、收益多维指标。
  - 权限体系：角色 + UserContext.requireAdmin() 双重校验，管理接口与用户接口在网关上物理隔离。
- 可演示点：AI 审核工作台处理一条风险弹幕 → 歌曲文件夹批量上传 → 首页轮播改成手动选题并预览 → 数据看板。
- 难点：审核队列与业务状态机的一致性；后台 20 个页面的表单/表格组件抽象；敏感操作（下架、驳回、禁言）的二次确认与留痕。

### 3. 广告达人端（成员C，即需求文档中的「广告制作人」）

- 覆盖页面：入驻申请、工作台首页、素材管理（音频/视频/图文三类素材）、投流计划（选广告位、投放时段、目标人群、按位按天报价）、投放数据、收益与提现。
- 后端归属：ad-service（入驻、素材、投放、数据、收益）+ file-service（素材上传 MinIO）+ user-service（角色开通）。
- 核心亮点：
  - 角色分工清晰：广告制作人做素材与投流，广告主付费买量，制作人拿投放收入并可提现——与需求文档一致，避免「广告主产生收益」的逻辑错误。
  - 计费闭环：投流费用按广告位 + 投放天数计费（广告位价格由后台维护），支付成功后才允许提交审核，审核通过才真正投放。
  - 四级广告位：开屏、首页 Banner、直播页、播放页，与用户端广告组件（AdSlot/AdSplash/AdModal）一一对应。
  - 数据回流：曝光/点击按配置比例折算收益，ad_stat_daily 按天聚合，工作台直出图表。
- 可演示点：入驻申请 → 上传视频素材 → 新建投流计划并支付 → 用户端开屏/播放页看到广告 → 工作台看曝光点击与收益 → 发起提现。
- 难点：素材多类型与大小限制校验、投放时段与目标人群的生效条件、结算口径（曝光 vs 点击）与后台审核的联动。

### 4. 主播端（成员D）

- 覆盖页面：主播入驻申请（身份证正反面 + 封面）、主播工作台、开播准备与预览、直播控制台（OBS/扫码推流、待唱队列、礼物、弹幕、在线人数、结束直播）、直播回顾报告、主播收益与收款账户/提现。
- 后端归属：live-service（直播间、弹幕 WebSocket、礼物、在线人数、回放）+ 依赖 file/search/vip/review 服务；流媒体由 SRS 承担。
- 核心亮点：
  - 低延迟直播：OBS RTMP 推流到 SRS，观众走 HTTP-FLV 低延迟、HLS 兜底；演示环境若无真实推流，live-service 自动调 ffmpeg 生成演示流，答辩现场也能跑通。
  - 互动与合规：弹幕 WebSocket 广播前必过 AI 审核，敏感词 DFA 命中不广播、落库交人工复核；Redis 维护在线人数与直播状态广播（STREAM_STATUS）。
  - 推流安全：HMAC-SHA256 推流鉴权，防止盗推；房间与主播绑定。
  - 收益闭环：礼物按 70% 折算主播收益，收款账户绑定 → 申请提现 → 管理员审核 → 负向流水。
  - 户外直播：支持户外场景创建房间、扫码推流与网络配置（移动网络下的推流参数）。
- 可演示点：开播 → 控制台设置待唱队列 → 观众端发弹幕（先被审核）→ 送礼物 → 结束直播 → 直播回顾报告 → 收益页发起提现。
- 难点：WebSocket 鉴权与断线重连、直播状态与回放的时序、审核导致弹幕延迟时的队列削峰。

### 5. 音乐人端（成员E）

- 覆盖页面：音乐人入驻（艺名/风格/身份证认证）、工作台、作品管理（歌曲上传、批量上传、上下架）、专辑管理、播放与粉丝数据、收益与提现、音乐人主页（用户端可见）。
- 后端归属：musician-service（入驻、作品、专辑、粉丝、收益、提现、播放统计）+ music-service（作品入库）+ file-service（音频/封面）+ search-service（同步索引）+ live-service（直播礼物收益）。
- 核心亮点：
  - 入驻即开通：审核通过自动获得音乐人角色并开通工作台权限，前端路由与后端接口同步放行。
  - 作品上架流水线：上传音频与封面 → 元数据填写 → 提交入库 music-service → 增量同步 ES → 用户端立即可搜可播。
  - 数据看板：播放趋势、粉丝增长、作品表现（ECharts），播放量来自 comment-service 的播放记录聚合。
  - 收益透明：每 1000 次播放折算 10 虚拟币 + 直播礼物 70% 分成，收益流水可查，提现走审核。
- 可演示点：入驻 → 上传一首歌并填元数据 → 用户端搜索到并播放 → 工作台看到播放量与粉丝变化 → 申请提现。
- 难点：音频时长/封面尺寸的自动校验、作品与歌曲表的幂等入库、播放量聚合口径（播放记录 vs 播放统计）。

## 五、五端如何协作（分端不等于分裂）

1. 契约先行：kumao-api 模块统一 Feign 客户端与跨服务 DTO，kumao-common 统一返回体、异常、JWT、用户上下文；任何跨端改动先改契约再改实现。
2. 网关收口：所有端只认一个入口 :8080，鉴权、限流、跨域、WS 转发集中一处，端内不再重复实现。
3. 公共能力复用：文件上传（MinIO）、AI 审核（review）、搜索（ES）、支付（vip）、认证（身份证正反面）五个能力被五端共享，谁先做谁沉淀，别人直接接。
4. 每日联调：按「用户端 ← 主播端/音乐人端/广告达人端 ← 管理员端」的依赖顺序联调，问题记在看板，按端认领。
5. 统一工程规范：Git 分支 + 提交信息规范、统一响应结构与错误码、统一 UI 设计令牌与组件（PC 与 APP 同源风格）。

## 六、成果量化

- 后端：288 个 Java 源文件，12 个可独立启动的进程，44 张数据表，11 个业务微服务 + 1 个网关。
- 前端：101 个 Vue 组件/页面；PC 端 57 条路由（用户端 + 20 个管理页面 + 工作台）；APP 28 个页面，Android APK 真机可装；Electron 桌面壳。
- 接口：docs/API接口清单.md 覆盖 11 个模块的全部接口，配套 8 份专题文档（架构、认证、支付、户外直播、内容安全、AI 审核台、部署、真机调试）。
- 环境：Docker Compose 一键拉起 9 类中间件；一条 start-all 脚本按顺序启动 12 个服务。

## 七、五个真实难点与解法

1. 微服务拆分的边界：按「业务对象」而非「页面」拆（歌曲/歌单/评论/直播/会员…），跨服务只走 Feign + DTO，禁止跨库查询；最终 11 个服务边界清晰、单人可维护。
2. 多端鉴权与设备隔离：JWT 带 device，Redis 按 device 维度存 token，网关统一透传，解决「同一账号 PC 与手机互踢」与「桌面专属接口」两个矛盾。
3. 直播低延迟与内容安全的两难：HTTP-FLV 保延迟、HLS 兜底；弹幕先审后播，审核超时走降级策略，既不卡直播也不放过风险内容。
4. 三方依赖不可用：ES 挂了降级 MySQL、AI 模型不可用降级本地规则、SRS 无推流时 ffmpeg 自动演示流——三层降级保证答辩现场「一定能演示」。
5. 真机联调：手机访问不到本机服务时，提供 USB（adb reverse）与 Wi-Fi 局域网两版 APK，并把 503/跨域/证书问题沉淀成排查文档。

## 八、后续规划

- 鉴权升级 RS256 非对称签名 + 网关公钥校验；榜单改实时计算（Flink）；播放记录与弹幕落 ClickHouse 做数据分析；直播增加连麦与实时字幕；广告接入真实广告主平台与反作弊。
